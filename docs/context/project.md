# Project

## Layout

- `Cargo.toml`: workspace root (members `crates/client`, `crates/server`, `crates/shared`, `crates/web_delta`, `xtask`); Bevy's default features are off at workspace level (the client turns them on, the server stays headless); `bevy_remote` is pinned to Bevy's exact locked version (`=0.20.0`, so adding it didn't move Bevy itself; raise them together) and, with `serde_json`, is only built with the `debug-api` features of `server` and `client`; shared dependency versions (`[workspace.dependencies]`) and build profiles live here.
- `crates/shared/`: library crate `shared` (plain Rust): rules and world generation. See `CLAUDE.md` table.
- `crates/server/`: package `server`, library (`ServerPlugin`, `start_embedded`) + binary `hall-of-worlds-server` (native only). See `docs/context/server/server.md`.
- Running a networked server locally: `trunk build` (the web client into `dist/`), then `HOW_WEB=dist cargo run -p server` and open https://localhost:24691 (sent on to `/web/`, the web client's `public_url` in `Trunk.toml`; the browser warns about the self-signed certificate; `HOW_BEHIND_PROXY=true` also opens plain http://localhost:24690); a native client joins it with `HOW_SERVER=wss://localhost:24691/ws`. `LOG_LEVEL=debug` also logs every round trip, for looking into network trouble (noisy, so not by default).
- Saved data (not in the repository): the server saves in `Hall of Worlds/server` in the user's data folder (`%APPDATA%` on Windows), or wherever `HOW_DATA` points; the embedded single-player server too. The client will keep its own data beside it (`Hall of Worlds/client`), never in the server's folder.
- `crates/web_delta/`: library crate `web_delta` (plain Rust, native only): `dcz` deltas of the web client's wasm for the server and xtask (`docs/context/web_delta/web_delta.md`).
- `crates/client/`: Bevy app, package `client`, binary `hall-of-worlds` (window title "Hall of Worlds"). Native builds depend on `server` (target-specific dependency) and start the embedded server for single player (`connection` module); the wasm build doesn't. `src/main.rs` creates the window (bound to `<canvas id="game">` on the web) and registers each module's plugin; no game logic. `build.rs` gives the Windows exe a name and version (`winresource`, a Windows-host build-dependency; needs the Windows SDK's resource compiler, and only warns without it), so the taskbar and the file's Details say "Hall of Worlds", not `hall-of-worlds`.
- `crates/client/assets/`: images, sounds, fonts. `ATTRIBUTION.md` credits third-party art (required by its licences; add an entry with any new third-party asset). `fonts/`: Lexend (the default font) and Noto Emoji (symbols), for the `fonts` module, and the title font (`loading_screen`), all built into the program. Only pictures the code names are kept here; whole sets are in `spare_assets/` (below), so using another means copying it in. `monsters/`: David E. Gervais's Dungeon Odyssey monster tiles in use (CC BY 3.0), 54×54 RGBA PNGs with lower-case names, for tokens' icons. `shaders/`: the WESL shaders of the world map and dungeon view. `angbandtk/`: the same artist's flat AngbandTk tiles in use, 32×32 PNGs named `<sheet>_<row>_<column>.png` (from the `dg_features32`, `dg_grounds32`, `dg_extra132` sheets), for dungeon walls and floors (`dungeon_map::theme`). `icons/`: game-icons.net icons drawn by `xtask icons`. `hall/marble.png` (`tools/make_marble.py`), `town_atlas.png`, `field_crops.png`, `herb_plants.png` (`tools/make_town_atlas.py`). Loaded by Bevy's `AssetServer`: native debug builds read an `assets` folder beside the exe if there is one (`cargo xtask latest`'s copy), and otherwise this folder directly (`asset_folder` in `main.rs`, an absolute compile-time path, so the exe works from `target/debug`); release builds look for `assets/` next to the executable, so every native release must ship it (`cargo xtask package` does); Trunk copies it into `dist/` for the web (and so the Docker image).
- `index.html` + `Trunk.toml`: the web build (points Trunk at `crates/client`). Serves on port 3000.
- `docs/`: the user documentation, Markdown built by Jekyll with the Just the Docs theme (`_config.yml`). See "User documentation" in `CLAUDE.md`.
- `docs/context/`: context files for Claude (this folder), left out of the site.
- `spare_assets/`: art kept in the repository but never shipped (not in `crates/client/assets/`, left out of the Docker context), with a `README.md`. `monsters/` (932) and `terrain/` (960, none used): the whole Dungeon Odyssey sets; `angbandtk/`: all 432 AngbandTk tiles, which `tools/make_town_atlas.py` reads. `game-icons/`: every game-icons.net icon as the project's SVGs (white on black), one folder per author, with `license.txt`; `cargo xtask icons` draws the ones in `xtask/icons.txt` into `crates/client/assets/icons/<author>/<name>.png` (128 × 128, white on transparent, `xtask/src/icons.rs`, with resvg).
- `tools/`: scripts run by hand: `make_town_atlas.py` (Python with Pillow) makes `assets/town_atlas.png`, `field_crops.png` and `herb_plants.png` from `spare_assets/angbandtk/`.
- `scenarios/`: debug API scenario files for `cargo xtask scenario` (`*.txt`).
- `xtask/`: helper commands, run as `cargo xtask <task>` via the alias in `.cargo/config.toml`. `xtask package` puts its files in `package/` in cargo's target folder, which `target_dir.rs` asks `cargo metadata` for. `xtask test` = fmt check + clippy `-D warnings` for native (`--workspace --all-targets`, then again with `--features client/debug-api,server/debug-api`) and for `wasm32-unknown-unknown` (`client` package, which pulls in `shared`) + `cargo test --workspace` with the debug API features + the file size check + the WebGL 2 check + the Dockerfile check + the icon check (every icon in `xtask/icons.txt` drawn, and nothing else in `crates/client/assets/icons/`) + no `"tmp.` debug API method names left in `crates/`. `xtask lint` = the same without the tests and the `tmp.` check. The file size check (`xtask/src/sizes/`) counts each `.rs` file's lines under `crates/` and `xtask/`, leaving out test files (`tests.rs`, `*_tests.rs`, `tests/` folders) and `#[cfg(test)]` modules (a `mod …;` line or a `mod … { }` block), and fails on any over 300 that isn't in `xtask/large-files.txt` (path, most lines, optional `# reason`), on a listed file that has grown past its entry, and on entries no longer needed; `xtask sizes` lowers entries to the files' sizes and drops those back under the limit, never adding or raising one. The WebGL 2 check (`xtask/src/webgl/`) reads the client's source for what would quit the web build while native works: every `#[derive(ShaderType)]` struct in `crates/client/src` laid out as a WGSL uniform (`layout.rs`; an unknown field type is an error, so teach it new types) must be a multiple of 16 bytes; `new_target_texture` must not be given a plain `Rgba8Unorm`/`Bgra8Unorm` format and hand-made `RENDER_ATTACHMENT` images are refused (`rules.rs`); shaders in `crates/client/assets/shaders/` may not use storage buffers or textures or `@compute`. The Dockerfile check (`xtask/src/dockerfiles.rs`) fails unless `Dockerfile` and `Dockerfile.github` both have the `# --- Same in Dockerfile and Dockerfile.github` line and match line for line after it (line endings and trailing blank lines aside). `xtask api` calls a running game's debug API (`docs/context/debug-api.md`); `xtask scenario <file> [--start]` (`xtask/src/scenario.rs`) plays a file of such calls, from `scenarios/` (one `api` line each; `--start` builds and starts a development copy for it). `xtask latest` (`xtask/src/latest.rs`) builds the client with the debug API and copies it into `latest/` in cargo's target folder as `hall-of-worlds-latest` (so `taskkill` of development copies leaves it, and it never locks a build), with `assets/` and `play.cmd` (`play.sh` elsewhere) starting it detached with `HOW_DEBUG_API=15712`; a running copy makes it fail before anything is touched: the owner's copy to play, made by Claude after each change instead of starting the game. `xtask compress-web <dir>`: brotli copies of a web build's files (see Web below). `xtask web-deltas <dir> <old wasm>...` (`xtask/src/web_deltas.rs`, the `web_delta` crate): a delta into `<dir>/deltas/<hash>.dcz` from each old build's wasm, for releases (from the wasm as published; the server also makes its own from the builds it served). `xtask fight [fights=N] [armour=N]` (`xtask/src/fight.rs`, the `shared` crate) prints how long fights between equal median creatures last with each kind of weapon, by `shared::combat`'s rules, for balancing. `xtask icons` draws the listed icons and removes PNGs no longer listed (see `spare_assets/` above). `xtask hooks` points git at `.githooks/`, whose `pre-commit` runs `xtask lint`. `xtask package` = release build of client + server, then `target/package/` with both executables and `assets/` (the layout players get; used by the manual Build workflow and the VSCode "Release build (native)" task).
- `Dockerfile`, `.dockerignore`: the server image, built entirely in Docker (for building it yourself). `Dockerfile.github`: the same image from what the Docker workflow compiled (see Docker below).
- `LICENSE`: CC BY-NC 4.0 (official legal text); `license = "CC-BY-NC-4.0"` in `Cargo.toml` for every crate.
- `README.md` (human setup, domains, game design, licence), `designs.txt` (older design notes).

## Tooling

- Rust stable, pinned via `rust-toolchain.toml` (also installs the `wasm32-unknown-unknown` target, clippy, rustfmt).
- `Cargo.toml`: dev profile builds our code at opt-level 1 and dependencies at 3 (Bevy is unusably slow unoptimised), with only line numbers as debug info for our code and none for dependencies (no debugger is used, and full debug info made each test program's `.pdb` about 1.2 GB). Library crates have `doctest = false`, as there are no doc tests. On Windows, `.cargo/config.toml` links with `rust-lld.exe` (comes with Rust) instead of `link.exe`. Release uses thin LTO. `web` (inherits `release`, thin LTO since fat ran GitHub's 16 GB runners out of memory, no debug info, stripped) is the browser build's alone, named by `--cargo-profile web` in the Dockerfile and the Build workflow, so native releases and development builds never use it.
- Web: Trunk (`cargo install --locked trunk`). `index.html` asks Trunk to run `wasm-opt -Os` in release builds. `cargo xtask compress-web <dir>` (`xtask/src/compress_web.rs`, the `brotli` crate) then writes `<file>.br` beside each file of the build that brotli (quality 11) shrinks by at least a tenth, leaving out images and other compressed kinds; the server sends those to browsers that take brotli. Local `trunk build`s have none, so get the plain files.
- Shaders (`crates/client/assets/shaders/`): every uniform struct must be a multiple of 16 bytes, padded with unused `f32`s in both the shader and its Rust `ShaderType`. WebGL 2 has no `BUFFER_BINDINGS_NOT_16_BYTE_ALIGNED`, so the web build refuses a short one and Bevy quits on the first frame, while native works; `picture_edge.wesl` (#130) and `sight_mask.wesl` broke the web build this way. Render targets must use an `Srgb` format: for plain `Rgba8Unorm`/`Bgra8Unorm` Bevy gives the camera's own textures an extra sRGB view, which needs `VIEW_FORMATS`, missing on WebGL 2. `cargo xtask lint` checks both.
- Windows needs the MSVC C++ build tools (installed: VS 2019 Build Tools). Linux needs alsa/udev/wayland/xkbcommon dev packages (see CI).

## VSCode

- `.vscode/tasks.json`: Run/Build native, Serve web, release builds, Test (default test task).
- `.vscode/launch.json`: F5 debugs the native build via CodeLLDB. With only line numbers built (see Tooling), breakpoints and stepping work but variables can't be inspected; set `debug = true` under `[profile.dev]` locally when that's needed.
- `.vscode/settings.json`: rust-analyzer uses clippy, format on save, separate target dir.
- Cargo's target folder can be outside the checkout (a cargo setting or `CARGO_TARGET_DIR`): on the owner's machine every checkout and worktree builds into one folder on another drive. Don't assume `target/debug` or `target/release` is in the workspace.

## Docker

- Multi-stage `Dockerfile`, x86-64 only (`linux/amd64`; ARM can be added later under the same tags): a `tools` stage `cargo install`s Trunk 0.22.1; `build` compiles `hall-of-worlds-server` (release) and the web client (`trunk build --release --cargo-profile web`, into `/srv/web`, then `cargo xtask compress-web /srv/web`); the runtime is `debian:trixie-slim` (same Debian as the `rust:1.99-trixie` builder, so glibc matches), non-root user `hall`. `HEALTHCHECK` runs `hall-of-worlds-server --health` (the binary asks its own plain port's `/_healthz` with the standard library), so the image needs no curl or wget and could move to a smaller base.
- `Dockerfile.github` makes the same image for the Docker workflow, which compiles the server and web client on the runner (with rust-cache) and builds it from a folder of just `hall-of-worlds-server` and `web/`: cache mounts in a Docker build don't survive between GitHub runs, so `Dockerfile` recompiled everything (and Trunk) every time, about 35 minutes. **Keep the two in step:** everything after the `Same in` marker line is identical (`cargo xtask lint` checks it); a change to `Dockerfile`'s build steps (Trunk's version, the build or compress commands) needs the same change in `docker.yml`, and usually `build.yml` too. The runner is pinned to `ubuntu-24.04` because the server is linked against its glibc (2.39), which must not be newer than trixie's (2.41).
- One process: the game server is the entrypoint and serves both the web client and the game's WebSocket on one port: 24691 over TLS, also 24690 with `HOW_BEHIND_PROXY=true` (without it, 24690 only answers with an error), and only 24690 with `HOW_DISABLE_SSL=true` as well (`HOW_ADDRESS=0.0.0.0:24690`, `HOW_WEB=/srv/web`). The generated certificate is kept in `/data/tls`, and anything from Let's Encrypt in `/data/tls/acme`. The image installs `ca-certificates` so the server can check Let's Encrypt's website. Saves go in `/data` (`HOW_DATA`, a `VOLUME`, owned by `hall`): mount a volume there to keep them across updates. The server handles SIGTERM (it is PID 1), saving everyone before it stops.
- Not testable locally (no Docker on the owner's machine), and CI only builds it after merging to `master`.

## Domains

- `hallofworlds.com`: landing page / adverts / email. `hallofworlds.app`: the owner's server running the Docker image. `hallofworlds.wiki`: game documentation, from `docs/` in this repo.

## CI

- `.github/workflows/test.yml` ("Check"): only `cargo check --release --workspace` on Linux, for pull requests that are ready for review (draft PRs are skipped) and on pushes to `master` (which warms the cache PRs reuse). Cut down from `cargo xtask test` on three OSes, which was too much work per PR; run that locally. The `All tests passed` job keeps its old name because it is the check required in branch protection (what auto-merge waits for).
- `.github/workflows/build.yml`: manual only (Run workflow in the Actions tab), `cargo xtask package` for the three OSes (client, server and assets) and the web client, uploaded as workflow artifacts (`hall-of-worlds-<OS>` = `target/package`, `hall-of-worlds-web` = `dist`, built and compressed as in Docker). Any branch; `nightly.yml` makes the daily ones.
- `.github/workflows/nightly.yml`: daily at 04:00 UTC or manually (`force` builds even with nothing new). Reads the commit `:latest` was built from (its `org.opencontainers.image.revision` label) and stops if `:nightly` already has it. Otherwise copies the web client and server out of `:sha-<short>` (no web rebuild) and runs `cargo xtask package` for the three OSes at that commit, as artifacts named `…-<date>-<short>` kept 14 days; once all have worked, the web client also gets deltas (`cargo xtask web-deltas`, from a checkout at that commit) from the wasm of the last `PAST_NIGHTLIES` (7) `nightly-<date>` images, listed with `skopeo` and copied out as served; once all have worked, the `tag` job pushes `:nightly` and `:nightly-<date>` as that image plus one layer of `/srv/web/deltas/` (or, with no deltas, `docker buildx imagetools create` points them at the same image), so a failed night is retried the next. `:latest` gets no deltas.
- `.github/workflows/docs.yml`: builds the user documentation with Jekyll for pull requests touching `docs/` (not `docs/context/`), and on `master` or manually also publishes it to GitHub Pages. No Ruby here, so that is the only build; the domain is in the repository's Pages settings.
- `.github/workflows/docker.yml`: on push to `master` (every merge, unless only `docs/` changed) or manually, builds and publishes `ghcr.io/rycochet/hall-of-worlds:latest` and `:sha-<commit>` using `GITHUB_TOKEN` (`packages: write`); run by hand on another branch it publishes only `:sha-<commit>`. Builds the server and web client on the runner with `Swatinem/rust-cache` and Trunk's release binary (downloaded and checked against its `.sha256`), then `Dockerfile.github` copies them in (no Docker layer cache: the layers are only copies). A merge during a build waits for it (`cancel-in-progress: false`), since cancelled runs saved no cache and kept every build from finishing.
