# Project

## Layout

- `Cargo.toml`: workspace root (members `crates/client`, `crates/server`, `crates/shared`, `xtask`); Bevy's default features are off at workspace level (the client turns them on, the server stays headless); `bevy_remote` is pinned to Bevy's exact locked version (`=0.20.0`, so adding it didn't move Bevy itself; raise them together) and, with `serde_json`, is only built with the `debug-api` features of `server` and `client`; shared dependency versions (`[workspace.dependencies]`) and build profiles live here.
- `crates/shared/`: library crate `shared` (plain Rust): rules and world generation. See `CLAUDE.md` table.
- `crates/server/`: package `server`, library (`ServerPlugin`, `start_embedded`) + binary `hall-of-worlds-server` (native only). See `docs/context/server/server.md`.
- Running a networked server locally: `trunk build` (the web client into `dist/`), then `HOW_WEB=dist cargo run -p server` and open https://localhost:8081 (sent on to `/web/`, the web client's `public_url` in `Trunk.toml`; the browser warns about the self-signed certificate; `HOW_BEHIND_PROXY=true` also opens plain http://localhost:8080); a native client joins it with `HOW_SERVER=wss://localhost:8081/ws`. `LOG_LEVEL=debug` also logs every round trip, for looking into network trouble (noisy, so not by default).
- Saved data (not in the repository): the server saves in `Hall of Worlds/server` in the user's data folder (`%APPDATA%` on Windows), or wherever `HOW_DATA` points; the embedded single-player server too. The client will keep its own data beside it (`Hall of Worlds/client`), never in the server's folder.
- `crates/client/`: Bevy app, package `client`, binary `hall-of-worlds` (window title "Hall of Worlds"). Native builds depend on `server` (target-specific dependency) and start the embedded server for single player (`connection` module); the wasm build doesn't. `src/main.rs` creates the window (bound to `<canvas id="game">` on the web) and registers each module's plugin; no game logic. `build.rs` gives the Windows exe a name and version (`winresource`, a Windows-host build-dependency; needs the Windows SDK's resource compiler, and only warns without it), so the taskbar and the file's Details say "Hall of Worlds", not `hall-of-worlds`.
- `crates/client/assets/`: images, sounds, fonts. `ATTRIBUTION.md` credits third-party art (required by its licences; add an entry with any new third-party asset). `fonts/`: Lexend (the default font) and Noto Emoji (symbols), for the `fonts` module, and Cinzel Decorative (`loading_screen`), all built into the program. `monsters/`: David E. Gervais's Dungeon Odyssey monster tiles (CC BY 3.0), 932 54×54 RGBA PNGs with lower-case names. `terrain/`: the same artist's Dungeon Odyssey terrain tiles, 960 54×54 RGBA PNGs, same treatment (`l2_terrain066`–`099` were the world map poi pictures, unused since pois became models). `fonts/`: Cinzel Decorative Bold (OFL), the loading screen's title, built into the client. `shaders/`: the WESL shaders of the world map and dungeon view. `angbandtk/`: the same artist's flat AngbandTk tiles, three spritesheets (`dg_features32`, `dg_grounds32`, `dg_extra132`) split into 432 32×32 PNGs named `<sheet>_<row>_<column>.png`, used for dungeon walls and floors (`dungeon_map::theme`). Loaded by Bevy's `AssetServer`: native debug builds read an `assets` folder beside the exe if there is one (`cargo xtask latest`'s copy), and otherwise this folder directly (`asset_folder` in `main.rs`, an absolute compile-time path, so the exe works from `target/debug`); release builds look for `assets/` next to the executable, so every native release must ship it (`cargo xtask package` does); Trunk copies it into `dist/` for the web (and so the Docker image).
- `index.html` + `Trunk.toml`: the web build (points Trunk at `crates/client`). Serves on port 3000.
- `docs/`: the user documentation, Markdown built by Jekyll with the Just the Docs theme (`_config.yml`). See "User documentation" in `CLAUDE.md`.
- `docs/context/`: context files for Claude (this folder), left out of the site.
- `tools/`: scripts run by hand: `make_town_atlas.py` (Python with Pillow) makes `assets/town_atlas.png`.
- `xtask/`: helper commands, run as `cargo xtask <task>` via the alias in `.cargo/config.toml`. `xtask package` puts its files in `package/` in cargo's target folder, which `target_dir.rs` asks `cargo metadata` for. `xtask test` = fmt check + clippy `-D warnings` for native (`--workspace --all-targets`, then again with `--features client/debug-api,server/debug-api`) and for `wasm32-unknown-unknown` (`client` package, which pulls in `shared`) + `cargo test --workspace` with the debug API features + the file size check + the WebGL 2 check + no `"tmp.` debug API method names left in `crates/`. `xtask lint` = the same without the tests and the `tmp.` check. The file size check (`xtask/src/sizes/`) counts each `.rs` file's lines under `crates/` and `xtask/`, leaving out test files (`tests.rs`, `*_tests.rs`, `tests/` folders) and `#[cfg(test)]` modules (a `mod …;` line or a `mod … { }` block), and fails on any over 300 that isn't in `xtask/large-files.txt` (path, most lines, optional `# reason`), on a listed file that has grown past its entry, and on entries no longer needed; `xtask sizes` lowers entries to the files' sizes and drops those back under the limit, never adding or raising one. The WebGL 2 check (`xtask/src/webgl/`) reads the client's source for what would quit the web build while native works: every `#[derive(ShaderType)]` struct in `crates/client/src` laid out as a WGSL uniform (`layout.rs`; an unknown field type is an error, so teach it new types) must be a multiple of 16 bytes; `new_target_texture` must not be given a plain `Rgba8Unorm`/`Bgra8Unorm` format and hand-made `RENDER_ATTACHMENT` images are refused (`rules.rs`); shaders in `crates/client/assets/shaders/` may not use storage buffers or textures or `@compute`. `xtask api` calls a running game's debug API (`docs/context/debug-api.md`). `xtask latest` (`xtask/src/latest.rs`) builds the client with the debug API and copies it into `latest/` in cargo's target folder as `hall-of-worlds-latest` (so `taskkill` of development copies leaves it, and it never locks a build), with `assets/` and `play.cmd` (`play.sh` elsewhere) starting it detached with `HOW_DEBUG_API=15712`; a running copy makes it fail before anything is touched: the owner's copy to play, made by Claude after each change instead of starting the game. `xtask hooks` points git at `.githooks/`, whose `pre-commit` runs `xtask lint`. `xtask package` = release build of client + server, then `target/package/` with both executables and `assets/` (the layout players get; used by the manual Build workflow and the VSCode "Release build (native)" task).
- `Dockerfile`, `.dockerignore`: the server image (see Docker below).
- `LICENSE`: CC BY-NC 4.0 (official legal text); `license = "CC-BY-NC-4.0"` in `Cargo.toml` for every crate.
- `README.md` (human setup, domains, game design, licence), `designs.txt` (older design notes).

## Tooling

- Rust stable, pinned via `rust-toolchain.toml` (also installs the `wasm32-unknown-unknown` target, clippy, rustfmt).
- `Cargo.toml`: dev profile builds our code at opt-level 1 and dependencies at 3 (Bevy is unusably slow unoptimised). Release uses thin LTO.
- Web: Trunk (`cargo install --locked trunk`). `index.html` asks Trunk to run `wasm-opt -Os` in release builds.
- Shaders (`crates/client/assets/shaders/`): every uniform struct must be a multiple of 16 bytes, padded with unused `f32`s in both the shader and its Rust `ShaderType`. WebGL 2 has no `BUFFER_BINDINGS_NOT_16_BYTE_ALIGNED`, so the web build refuses a short one and Bevy quits on the first frame, while native works; `picture_edge.wesl` (#130) and `sight_mask.wesl` broke the web build this way. Render targets must use an `Srgb` format: for plain `Rgba8Unorm`/`Bgra8Unorm` Bevy gives the camera's own textures an extra sRGB view, which needs `VIEW_FORMATS`, missing on WebGL 2. `cargo xtask lint` checks both.
- Windows needs the MSVC C++ build tools (installed: VS 2019 Build Tools). Linux needs alsa/udev/wayland/xkbcommon dev packages (see CI).

## VSCode

- `.vscode/tasks.json`: Run/Build native, Serve web, release builds, Test (default test task).
- `.vscode/launch.json`: F5 debugs the native build via CodeLLDB.
- `.vscode/settings.json`: rust-analyzer uses clippy, format on save, separate target dir.
- Cargo's target folder can be outside the checkout (a cargo setting or `CARGO_TARGET_DIR`): on the owner's machine every checkout and worktree builds into one folder on another drive. Don't assume `target/debug` or `target/release` is in the workspace.

## Docker

- Multi-stage `Dockerfile`, x86-64 only (`linux/amd64`; ARM can be added later under the same tags): a `tools` stage `cargo install`s Trunk 0.22.1; `build` compiles `hall-of-worlds-server` (release) and the web client (`trunk build --release`, into `/srv/web`); the runtime is `debian:trixie-slim` (same Debian as the `rust:1.99-trixie` builder, so glibc matches), non-root user `hall`. `HEALTHCHECK` runs `hall-of-worlds-server --health` (the binary asks its own plain port's `/_healthz` with the standard library), so the image needs no curl or wget and could move to a smaller base.
- One process: the game server is the entrypoint and serves both the web client and the game's WebSocket on one port: 8081 over TLS, also 8080 with `HOW_BEHIND_PROXY=true` (without it, 8080 only answers with an error), and only 8080 with `HOW_DISABLE_SSL=true` as well (`HOW_ADDRESS=0.0.0.0:8080`, `HOW_WEB=/srv/web`). The generated certificate is kept in `/data/tls`, and anything from Let's Encrypt in `/data/tls/acme`. The image installs `ca-certificates` so the server can check Let's Encrypt's website. Saves go in `/data` (`HOW_DATA`, a `VOLUME`, owned by `hall`): mount a volume there to keep them across updates. The server handles SIGTERM (it is PID 1), saving everyone before it stops.
- Not testable locally (no Docker on the owner's machine), and CI only builds it after merging to `master`.

## Domains

- `hallofworlds.com`: landing page / adverts / email. `hallofworlds.app`: the owner's server running the Docker image. `hallofworlds.wiki`: game documentation, from `docs/` in this repo.

## CI

- `.github/workflows/test.yml` ("Check"): only `cargo check --release --workspace` on Linux, for pull requests that are ready for review (draft PRs are skipped) and on pushes to `master` (which warms the cache PRs reuse). Cut down from `cargo xtask test` on three OSes, which was too much work per PR; run that locally. The `All tests passed` job keeps its old name because it is the check required in branch protection (what auto-merge waits for).
- `.github/workflows/build.yml`: manual only (Run workflow in the Actions tab), `cargo xtask package` for the three OSes (client, server and assets) and the web client, uploaded as workflow artifacts (`hall-of-worlds-<OS>` = `target/package`, `hall-of-worlds-web` = `dist`).
- `.github/workflows/docs.yml`: builds the user documentation with Jekyll for pull requests touching `docs/` (not `docs/context/`), and on `master` or manually also publishes it to GitHub Pages. No Ruby here, so that is the only build; the domain is in the repository's Pages settings.
- `.github/workflows/docker.yml`: on push to `master` (every merge, unless only `docs/` changed) or manually, builds and publishes `ghcr.io/rycochet/hall-of-worlds:latest` and `:sha-<commit>` using `GITHUB_TOKEN` (`packages: write`). Uses the GitHub Actions layer cache.
