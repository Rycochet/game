# shared: protocol

The messages between clients and the server, and the `Link` that carries them. Clients send intents; the server sends what the player may know. Design: "Map data" in `architecture.md`.

## Public API

- `SOCKET_PATH` (`/ws`): where a server's WebSocket is.
- `VERSION_PATH` (`/_version`), `GAME_NAME`, `ServerVersion`: what a server says it is, so a client can check an address is a Hall of Worlds server speaking its protocol before connecting.
- `PROTOCOL_VERSION`: bump whenever a message changes; the server refuses other versions. 103: `QuestNews::Escort` (`movement::Gait` now serde). 102: `quest::DungeonWay::Hidden`. 101: quest dungeons (`QuestAsk::Enter`, `quest::Target::Dungeon`, `story::PlaceKind::Cellar`). 100: quest bosses' looks (`EntityLook::boss`, `mob::BossLook`). 99: Collect steps (`Hook::Collect`, `story::Facts::remains`, `ItemKind::Remains`). 98: found quest items (`QuestNews::Finds`, `FindMark`; `Slain` became `Ahead(Vec<DoneAhead>)` with `Ahead::{Slain, Found}`, `OfferState::Available::ahead`, `Hint::Ahead`; `ItemKind::Keepsake`). 96: quest items (`Item::quest`, `ItemKind::Parcel`). 95: castles (`WallLook::{towers, gaps}`, `PoiLook::Building::castle`). 94: quest bosses (`QuestNews::{Bosses, Slain}`, `OfferState::Available::dealt_with`, `Hint::DealtWith`). 92: `QuestNews::Dots`. 91: `Trait::Markings` (a new look, so a new value in every `Appearance`). 90: the Quest Log (`Marker::Taken`, `QuestAsk::{PlanetLog, Planets, Track}`, `QuestNews::{PlanetLog, Tracked}`, `Log::tracked`, `DailyDone`'s giver and town, `PlanetQuests`' code, here and taken). 89: `ServerMessage::CharacterRefused`. 88: quest offers name their giver, `QuestNews::Planets`. 84: positions in units on levels (`Move`, `Moves`, spots in `LevelInfo::arrival` and `EnterHall`). 78: doors; 79: locks; 80: Kick (`Landed::Door { left }`: a kick landed on a door, `target` `None`, per mille left, 0 broken). 81: the debug menu cleanup (`DevToHall { seed, gate }` and `DevSkills { who, change }` with `DevSkillsOf`, changed in its PRs 1 and 2 without a bump; `Welcome`'s `debug_tools`). 82: `DevToShowcase` gone with the POI Showcase. 87: quests (`ClientMessage::Quest`, `ServerMessage::Quest`).
- `ClientMessage::Door(DoorAsk)` (`door_ask.rs`, 78): `Open { x, y }` (the closed door beside the player: away from them, a found secret door towards them), `CloseNear` (every open door beside them with nothing in its doorway; the L key), `DevAll { open }` (dev tools: every door of the level), `DevKey` (dev tools: keys for the locks beside the player, or the nearest). `Open` unlocks a locked door first if the player carries its key; `CloseNear` also locks the closed doors beside them whose key they carry. Queued with steps. `ServerMessage::DoorRefused { x, y, locked }`: an `Open` refused (not beside the player, a secret door they haven't found, or `locked` without its key), so click travel stops; an already open door is only sent again.
- Combat (55; 57: Heal; 58: `Harmed`): `ClientMessage::UseAbility { ability, target }` (`target` `None` for the player themselves; answered with `AbilityStarted` or nothing), `CancelAbility` (one winding up), `WithdrawAbility` (one still waiting in `Client::waiting` for the energy; not answered, never one begun); `ServerMessage::AbilityStarted { who, ability, target, lands_in, ready_in }` (`who` and `target` `None` meaning the player; ticks from now), `AbilityLanded { who, target, landed: Landed }` (`Landed::{Hit { harm, left }, Fizzled, Cancelled, Healed { amount, left }}`, `left` per mille for health bars), `Killed { permanent }` (63: `permanent` on Ironman, when the character has been deleted and `Characters` follows), `Harmed { id, left }` (someone in sight harmed by a blow the player neither struck nor took). A player is told of their own abilities and of those aimed at them, and of harm to anyone else they see.
- `WORLD_MAP_SIGHT` (300): how far (each way) the client may show anything on the world map. `WORLD_MAP_PRELOAD` (one chunk, 64): how much further the server sends.
- `ClientMessage::GiveItem { item, to }`: something carried to a mob within `mob::GIVE_REACH` and in sight; answered with `Inventory`, and the mob's `EntitySeen` again if its feeling changed.
- `ClientMessage::MoveItem { item, to, x, y, rotation }`: something carried to this place in this grid; `StackItem { item, onto }` (as much of a carried stack as fits onto another that looks the same, from its top); in these and in `GiveItem`, `WearItem` and `DropItem`, an id from inside a stack stands for it and everything above it (splitting: `Inventory::part_of`); `FromStack { stack, items, then }` wraps one of them for a group from a mixed stack (`Inventory::lift_group`); `PartOfStack { stack, count, then }` the same for the top `count` of a stack (`Inventory::lift_count`), sent for counted stacks (coins), whose part is new: the server gives it an id and puts it in `then` in place of the client's stand-in; `SortGrid { holder }` (`Inventory::sort_grid`: stacked, then laid out again largest first, or nothing if something wouldn't fit); `BinItem { item }` (with all in it, destroying what was there); `WearItem { item }` (what is in its way comes off: `wear_swapping`; refused with `ServerMessage::NotWorn { item, why }`, a `WearRefused`, before the `Inventory` putting it right); `DevGiveItem(DevGive { kind, size, magical, quality, set, favour, seed, count, identical, request, to })` (`dev_give.rs`; `to`: a mob or another player in sight, made for them, or `None` for the character; rolled by `item_form::try_make_item` from `seed` with the `RollRequest`, nothing given if any is refused, or a random one; `count` kept to the server's `StackLimits`) and `DevSetCreature { kind, how }` (dev tools; `KindChange::{Permanent, Temporary}`, `kind_change.rs`). `DevDeleteCharacter` (dev tools): the character's save is deleted and the account given a new character, answered with `Characters` with none to choose, as on first joining. All answered with `ServerMessage::Inventory` (also sent after `Welcome`, with `Sheet` and `VisitedGates`, only ever about the player's own character), whether or not they could be done, so the client is put right.
- **The map's measure** (84): `Position`, `Teleported`, `DevTeleport`, `EntityLook`'s `x`, `y` and `Stretch`es are world map points on the world map, and on a site level, in the wilderness and in the Hall units of 240 a cell (`spot::Spot`; a cell's middle at `(x, y) × 240`), in the Hall counted from `origin × 240`. `ClientMessage::Move { map, number, to: Spot }`: a straight move on a level or in the Hall from where the server has the player (counted with steps), taken if `movement::move_on_level` allows it (the cell rule between two cells' middles, else the segment rule), at most `MOST_MOVE` long; `Step` is the world map's only.
- `ServerMessage::EntitySeen(EntityLook)`, `Moves(Vec<Stretch>)`, `EntityGone { id, died }`: mobs and other players coming into sight, moving and going, only while in the player's sight; `Moves` is at most one a tick, with a `Stretch` (from, to, ticks it takes, from when it is received) for everyone in sight who moved, so headings can come from it; `died` when it went by dying, which only those who could see it are told (`ServerWorld::died`). `EntitySeen` is sent again when what can be seen of what one wears changes, as for its feeling. A map change forgets them on both sides. A `Moves` with one stretch is about 32 bytes.
- Difficulty (61; `shared::difficulty`): `ClientMessage::SetDifficulty(Difficulty)` (only to one allowed, never to or from Ironman; always answered), `SetDifficulties(Difficulties)` (only from roles with `Permission::ServerOptions`, such as the embedded server's host, ignored while `HOW_DIFFICULTIES` sets them; everyone on one no longer allowed is moved to the nearest); `ServerMessage::Difficulty { current, allowed }` (`current` `None` while making a character): after `Welcome` (after `Inventory`), after `SetDifficulty`, and to everyone playing or making a character when the allowed ones change.
- `ServerMessage::Sneaking(bool)`: whether the player sneaks, after `UseAbility` of `Sneak` (a toggle, answered with this rather than `AbilityStarted`); not kept, so off on joining.
- `ClientMessage::ActionBar(BarChange)`: change the action bar (`shared::ability`); always answered with `ServerMessage::ActionBar(ActionBar)`, the bar as it now is, so a refused change is put right. `ActionBar` is also sent on joining, after `Sheet`.
- `ClientMessage::DevDetectMonsters(bool)` (dev tools): every mob on the level is told of, seen or not.
- `ClientMessage::DevTruesight(bool)` (dev tools): items' secrets and secret doors are sent, without being found out. Answered with `Inventory`, what is on the ground under the player is told again, and the level is sent again if it has secret doors (which closes panels on it).
- `ClientMessage::DevGodMode(bool)` (dev tools): mobs take no notice of the character, who can walk through them.
- `ClientMessage::DevKillMob { mob }` (dev tools): a mob in sight dies; what it had falls where it stood.
- `ClientMessage::DevSkills { who, change }` (dev tools, the debug menu's Learn Skills: the character's skills, or with `who` another player's in sight, done once messages are read; `DevSkills::{Ask, LearnSome (DEV_SKILLS_LEARNT random ends of branches practised), Clear, Learn(id), Forget(id), Set { skill, percent }, SetAll(percent)}`): answered with `ServerMessage::DevSkillsOf { who, skills }` to the asker and `Sheet` to whoever changed. A `Sheet`'s skills carry each node's best, last use and rust clock too (64).
- `ClientMessage::DevVitals(DevVitals::{Hurt(n), SpendMana(n), Fill, Bonus})` (dev tools; `DEV_BONUS` 5 for `DEV_BONUS_TICKS`, 5 minutes): answered with `Vitals`.
- `ClientMessage::DevAlignment(DevAlignment::{Ask, Shift(n), Set(n)})` (`protocol/dev_alignment.rs`; dev tools, the debug menu's Alignment panel; `Ask` isn't audited): answered with `ServerMessage::DevAlignment(Alignment)`, the only message carrying a character's alignment (`shared::alignment`); every `Sheet` sent has it stripped (`Sheet::as_sent`). `PROTOCOL_VERSION` 86.
- `ServerMessage::Vitals { who, health, mana }` (`shared::vitals::VitalNow` each): `who` is `None` for the player's own, after `Sheet` in every welcome and whenever how much there is or can be changes other than by refilling, which the client works out itself; a party member's id later (owner, 2026-11-06).
- `ServerMessage::Borders(cells)`: with each wilderness window, after `Fields`: the window's cells round the cutouts of pois the player knows (`wilderness::Cutout::border`), drawn hatched; a click on one walks there and sends `Up`.
- `ServerMessage::FlatGround(Vec<movement::FlatGround>)` (68; meaning changed at 77): the groups of covered cells in pois' cutouts kept level (`wilderness::Cutout::flats`), their rectangles, each sent with the first of its cells the client is sent in a window (more than once is harmless: the client keeps each once), for drawing and step costs.
- `ServerMessage::PoiFound { kind }`: the player has just found a poi in the wilderness (its way in seen, or stepped inside it); never for towns. Shown by `notices`.
- `ServerMessage::Keepers`: who keeps each shop of a town level, after `Buildings`. `ClientMessage::OpenTrade { with }`: trade with someone (a shop's keeper, from beside its door), after any steps to get there. Answered with `ServerMessage::TradeStock { with, items }` if it can be, otherwise with nothing. `GiveItem` to a keeper also answers with `TradeStock` after `Inventory`. `ClientMessage::TakeItem { with, item, to, x, y, rotation }`: take from them, answered with both whether or not it could be done.

Quests are named by `QuestId` alone; alignment, hidden requirements and endings before turn-in are never sent.

## Notes

- A `Link` carries postcard-encoded bytes, not the messages, also in single player: nothing can be shared between client and server by accident, and over the network the same bytes are one WebSocket binary message each.
- When adding a message, add one of it to the round-trip test (`every_message`).
- Compiles for wasm: the web client uses the same types and `wired()` links over the browser's WebSocket.
- Facing (PR 9): `EntityLook::heading`; a `Stretch` turns its creature the way it goes; `ServerMessage::Turned(Vec<(Id, Heading)>)` only for other turns, one message a tick at most; `ClientMessage::Face(Heading)` the player's own turn in place (free and at once, not answered). `PROTOCOL_VERSION` 85.
