# server

The authoritative game simulation. Native only, never in the browser. Clients connect over WebSockets (`network`, which also serves the web client's files on the same port, over TLS unless behind a proxy), or in-process for single player. It runs a world (from its secret `WorldSeed`) and answers clients through `shared::protocol` messages: welcoming them, sending the world map chunks (pois) coming into each player's sight, and running their visits to sites (entering, stairs, leaving) while sending each level's cells as they come into sight. It checks every step a player takes (`shared::movement`) and tells the client where it has them. It saves the world, the sites entered and each character (what they know, where they are) in its own data folder, so a player continues where they left off. Mobs come next (see "Map data" in `architecture.md`).

- `crates/server/src/network.rs`: `NetworkPlugin { address, web, security }`: binds the ports at build (a port in use stops the server, as does a bad certificate), then a "network" thread runs a small `tokio` runtime with `axum`. `game_routes`: `/ws` (`shared::protocol::SOCKET_PATH`) upgrades to a WebSocket (`MAX_MESSAGE` 64 KiB), `/certificate` gives the public certificate as PEM (secure port only), anything else is a file from `web` (`tower-http` `ServeDir`), if given. Behind a proxy these are on `address`. Otherwise `TlsListener` serves them securely (handshakes run apart, within `HANDSHAKE_LIMIT`, so a slow client holds up nobody; own files are checked every `CHECK_FILES_EVERY`, an hour) and `address` answers everything with `426` naming the secure port (`use_the_secure_port`). Each WebSocket gets a `wired()` link, handed to the Bevy world through `NewConnections` and added by `accept_connections` (before `handle_messages`), to log in; `carry` moves binary messages both ways (a thread waits on the wire's outgoing side), answers game `Ping`s itself, without waiting for a tick, from the world's `WorldClock`, sends WebSocket pings every `PING_EVERY` (1 s), which time the connection and keep proxies from closing idle sockets, logs a connection going into or out of trouble, drops one with nothing heard for `SILENT_AFTER` (30 s) or not taking what is sent, and closes when either side goes. Sockets use `TCP_NODELAY`, so small messages aren't held back. Tests: pings answered with no game running, the rest reach the link, silent clients dropped, answering ones kept, the plain port's error, the certificate served being the one in use, the game over `wss://`, domain checks answered and kept apart from players. - `crates/server/src/latency.rs`: `Pings` (numbers a client can't guess for WebSocket pings, and times the answers), `Latency` (average round trip and how much it varies; `measured`, `no_answer` say when a connection goes into or out of trouble). - `crates/server/src/embedded.rs`: `start_embedded(WorldSeed, data) -> (ClientLink, EmbeddedServer)`: single player, character `player`, stops when its client has gone. `EmbeddedServer`: dropping it waits for the thread (drop the link first). Test: welcomes its client, and saves when it leaves.
- `crates/server/src/main.rs`: the standalone binary `hall-of-worlds-server`: `headless_app` (saving in `default_data_folder()`) plus `log_plugin()` and `NetworkPlugin`. ## Notes

- Embedded, the server runs on its own thread ("server") as its own Bevy `App`, so it shares no components or resources with the client: everything goes through the `Link`. The `App` is built on that thread (it can't move between threads). It adds no log plugin (the client's is used; only one can exist per process). When the client hangs up (on quitting) it saves and stops, and the client waits for it; if the process is killed, at most `SAVE_EVERY` of play is lost.
- Saves from before `shared::site::FORGET_BEFORE` are ignored when loaded and saved over: characters start again, sites are made new at the current versions. `world.ron` stays, as the world comes from its seed.
- For now every poi is sent to everyone (`world_map::ALL_POIS_KNOWN`, the owner's choice: a TODO until characters can learn of them). With it off, pois are hidden until known (`world_map::known_poi`): towns are seen by all, the rest only with `KnownPoi::known` or `visited`, or after `DevRevealPois` (this connection only). Nothing sets `known` yet. Entering (`enter_poi`) checks the same thing, as a client could otherwise enter one it was never told of.
- What a character knows (world map chunks seen, with or without a poi: all sent again on connecting, for the player's map; cells of each level seen) and where they are is saved; what the client has been sent is per connection. A site's generator version is fixed when it is first entered (one per site, not per level: a site's levels must agree on their stairs). `changes` are applied but nothing makes any yet; `last_visit` is recorded for resets, which come with spawns. Dev tools sites are saved too (`SiteId::Dev`).
- Tests that need saving use `TestFolder`; everything else uses `ServerWorld::new` (nothing saved). Runs for checking visuals should set `HOW_DATA` to a scratch folder, so they don't move the owner's character.
- Movement is steps only (`ClientMessage::Step`): the server never takes a position from a client. There is no speed limit yet (as many steps as arrive). On the world map, water stops steps, and the server's clock sets the tide.
- Other levels: on coming into a site (`enter_site`, also on resuming), `send_other_levels` sends each other level the character remembers as a `RememberedLevel`, generating it with its changes. Taking stairs sends none: the client keeps what it had.
- Towns: the whole level is sent on entering, marked `remembered`, after `Buildings`; nothing goes into the character's memory, and `update_sight` only sends cells that have changed since (no sight is worked out).
- A saved world at world map version 1 carries on: version 2 only turned some pois into towns.
- Sites and generator changes: a site keeps the version it was first made with, so a bump alone changes nothing while that version can run. It changes when the site is forgotten (`ServerWorld::forget_site`, `forget_sites`, from `DevForgetMapOnServer`, which delete the files) or its version can't run any more (`make_site` makes it anew). `CharacterWorldSave::site_versions` records the version each character knew: entering one that differs drops their memory of it, and coming back inside one (`resume`) puts them out at the poi (`OnWorldMap`) to go in again. Anyone else inside when a site is forgotten is put out the same way by `handle_messages`; whoever asked for it stays, arriving on the new map on the same level and cell if they can. A world map model always shows the current generator, so it can differ from an older site until that is forgotten.
- Levels are generated again on every visit (and the other level of each staircase, to work out its way down); cheap so far.
- Uses the filesystem (saves), one reason the web client must not contain it. Its data folder is its own, never shared with a client's (a client's data will go beside it, in `Hall of Worlds/client`).
- Latency is only known on the network thread and only logged, for now. A client can look slower than it is by answering late, so it must never earn anything. Handing it to the game (say, to scale `LEVEL_PRELOAD_STEPS`) is for when something needs it.
- In Docker it is the only process: it serves the web client and the game on port 8081, or 8080 with `HOW_BEHIND_PROXY=true` (`Dockerfile`).
- A browser checks certificates itself and warns about a self-signed one, which a page can't change. The embedded server never uses TLS: it has no network.
- Characters over the network belong to accounts, and only guests can log in so far; anything else is reached only by tests (`LoginKey::Test`). When an account connects again, the older connection is refused ("playing somewhere else") and saved first, then the new one loads the character: `handle_messages` welcomes a client only once its character is decided (`join`), stopping its messages there for that tick. So an account plays one character at a time. The embedded server's one client has no account and is `player`.
- A character belongs to the server, not a world: its file says which world they are in and holds what they know of each one. A server runs one world so far, so someone in another moves to it on loading (a stopgap: a server running several would put them back in theirs).
- When embedded in the client, the client's full Bevy features are active too (Cargo unifies features); that's fine.
