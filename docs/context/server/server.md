# server

The authoritative game simulation. Native only, never in the browser. Clients connect over WebSockets (`network`, which also serves the web client's files on the same port), or in-process for single player. It runs a world (from its secret `WorldSeed`) and answers clients through `shared::protocol` messages: welcoming them, sending the world map chunks (pois) coming into each player's sight, and running their visits to sites (entering, stairs, leaving) while sending each level's cells as they come into sight. It checks every step a player takes (`shared::movement`) and tells the client where it has them. It saves the world, the sites entered and each character (what they know, where they are) in its own data folder, so a player continues where they left off. Mobs come next (see "Map data" in `architecture.md`).

## Files

- `crates/server/src/lib.rs`: `ServerPlugin { world_seed, options, data }` (`data`: the data folder, `None` saves nothing), `ServerOptions { dev_tools, exit_when_alone }` (resource: whether `DevEnterSite` is accepted, and whether to stop once the last client has left; both only for the embedded server), `headless_app(seed, options, data)` (no window, `MinimalPlugins` ticking at `TICKS_PER_SECOND` 20), `ServerWorld` (resource: the world's seed, its `PoiMap`, width, `WorldGround`, `Storage`, and the `SiteSave`s loaded so far; `new(seed)` saves nothing (tests), `open(seed, storage)` loads `world.ron` or creates it, refusing a newer save format, another seed or a world map version it can't run; `site(id, kind)` loads or makes a site's save (new ones get the generator's current version), `site_mut` also marks it to save, `save_sites`; `info()` is what joining clients are told), `DEFAULT_WORLD_SEED` (12345, until worlds can be created and chosen), `SAVE_EVERY` (5 s), the world's `clock` (float game hours, always running, by `shared::world::GAME_HOUR_SECONDS`) and its whole `hour`, saved in `world.ron` each hour, `LEVEL_PRELOAD_STEPS` (3: how many steps ahead in a site the server sends what could be seen; a constant to become a server option), `exit_when_alone`.
- `crates/server/src/storage.rs`: the save files (RON, pretty-printed). `default_data_folder()` (`HALL_OF_WORLDS_SERVER_DATA`, else `<user data>/Hall of Worlds/server`, e.g. `%APPDATA%`; else `./server-data`), `Storage` (one world's folder `worlds/<id as 16 hex digits>/`, or none: load/save `world.ron`, `sites/<site>.ron`, `characters/<name>.ron`; a site or character file that can't be read is renamed `.ron.broken` and started again; writes go through a `.ron.new` file and a rename), `SAVE_FORMAT` (1), `WorldSave { format, seed, world_map_version, hour, clock }`, `SiteSave { version, levels: index → LevelSave { last_visit, changes, buildings: id → BuildingSave { trades, last_interaction } } }` (`buildings`: the player-made part of a town's buildings; nothing writes it until trading exists), `CharacterSave { world_position, visit: Option<VisitSave { site, level, position }>, pois: chunk → KnownPoi { visited }, memory: site → level → CellMasks }`, `SiteId::{Poi(chunk), Dev { kind, seed }}`, `CharacterName` (letters, digits, `-`, `_`: it is the file name), `CellMasks`, `Unsaved<K>` (keys to save), `now()`. `TestFolder` test helper (a temporary data folder). Tests: read back, missing fields default, broken files put aside, safe names.
- `crates/server/src/connections.rs`: `Connections` (resource; `add(link, name)`: the character is chosen by whoever accepts the connection, `is_empty`), `Client` (link, `CharacterName`, whether welcomed, its `CharacterSave` and whether it is unsaved, current `Visit`, world map chunks sent this connection, the map count and the last step this tick; `changed_map()` before telling the client it is on another map, `send_position`), `handle_messages` (after a client's messages, sends `Position` if steps arrived; forgets clients that have gone, saving them and the sites first), `save_changes` (every `SAVE_EVERY`), `run_clock` (every tick; on a new whole hour saves and sends `Hour` to everyone welcomed), `Ping` answered with `Pong`, `answer` (`Hello` only marks the client joining (named from its guest number if it has no name); `handle_messages` then `join`s it, dropping any older connection of the same character first; dev tools messages are ignored, with a warning, unless `ServerOptions::dev_tools`; `Hello`: loads the character, `Welcome { world, x, y }`, then resumes their visit if they were in a site, or sends the world map around them; `Step`: ignored if meant for another map, else to `sites` or `world_map`; `Refused` on a protocol mismatch, a second hello or anything before `Hello`; hands the rest to `world_map` and `sites`). `TestClient` test helper (`new`, `of(world)`, `welcome` (the answers to `Hello`), `dev_tools` (on unless set), `send` (one tick), `steps`, `walk_to`, `client_map`, `leave`). Tests: messages before hello refused, steps answered with the position once a tick, steps for another map ignored, guests named by their hello and the newest connection wins.
- `crates/server/src/world_map.rs`: `stepped` (not into open water, by `shared::movement` and `ServerWorld::conditions`: the hour's tide and the snow line, which `DevSnowLine` sets and isn't saved; a refused step is logged and left for `Position` to put right), `START` ((0, 0): where new characters start), `teleport` (dev tools, on the world map: `Teleported`), `back_to_start` (dev tools: out of any site to `START`: `OnWorldMap`), `look_around` (makes the pois in `WORLD_MAP_SIGHT` known to the character, sends each chunk within `WORLD_MAP_SIGHT + WORLD_MAP_PRELOAD` not sent yet, pois as `SeenPoi`; on joining, stepping, leaving a site, teleporting). Tests: sent on joining and once, moving sends only new ones, teleports and back to the start, dev tools ignored where not allowed, pois in sight known.
- `crates/server/src/sites.rs`: `Visit` (poi, `SiteId`, `Site`, level, its `SeenStairs`, position, cells sent; `save()`). `enter_poi` (the chunk's poi, if the player is within `ENTER_REACH`, the near way round the planet; marks it visited), `dev_enter`, `resume` (a saved visit: back on the same cell if still walkable), `enter_site` (generates the site with the version in its `SiteSave`; can't run it → stays out), `stepped` (only onto walkable cells; a refused step is logged and left for `Position` to put right), `teleport` (dev tools: any walkable cell of the level, through walls: `Teleported`), `use_exit` (stairs to another level, or edge ground to the world map: `OnWorldMap`, then `world_map::look_around`), `leave` (stamps the level's `last_visit`), `enter_level` (applies the level's saved `changes`, stamps `last_visit`, sends `EnterLevel`, then the remembered cells, then what is in sight), `update_sight` (what the player glimpses goes into the character's memory; what is glimpsed from every cell `nearby_cells` within `LEVEL_PRELOAD_STEPS` is sent if not yet), `send_cells` (secret doors as wall, stairs included). Tests (walking with a shortest-path helper): entering, sent once and remembered next time, dev teleports (through walls, not into them, and back to the start), steps into walls refused, stairs and the way out (and old steps ignored after), nearby cells stop at walls, coming back resumes the visit with its memory, `Welcome` before the level, changes applied, versions kept, last visit recorded.
- `crates/server/src/network.rs`: `NetworkPlugin { address, web }`: binds the port at build (a port in use stops the server), then a "network" thread runs a small `tokio` runtime with `axum`: `/ws` (`shared::protocol::SOCKET_PATH`) upgrades to a WebSocket (`MAX_MESSAGE` 64 KiB), anything else is a file from `web` (`tower-http` `ServeDir`), if given. Each WebSocket gets a `wired()` link, handed to the Bevy world through `NewConnections` and added by `accept_connections` (before `handle_messages`) as a guest; `carry` moves binary messages both ways (a thread waits on the wire's outgoing side), pings every `PING_EVERY` (30 s) so proxies keep idle sockets open, and closes when either side goes. Ctrl+C or SIGTERM sets `StopAsked`: `stop_when_asked` disconnects and saves everyone (`Connections::disconnect_all`), then exits.
- `crates/server/src/embedded.rs`: `start_embedded(WorldSeed, data) -> (ClientLink, EmbeddedServer)`: single player, character `player`, stops when its client has gone. `EmbeddedServer`: dropping it waits for the thread (drop the link first). Test: welcomes its client, and saves when it leaves.
- `crates/server/src/main.rs`: the standalone binary `hall-of-worlds-server`: `headless_app` (saving in `default_data_folder()`) plus `LogPlugin` and `NetworkPlugin`. Environment: `HALL_OF_WORLDS_ADDRESS` (default `0.0.0.0:8080`), `HALL_OF_WORLDS_WEB` (the web client's folder, e.g. `dist`), `HALL_OF_WORLDS_SERVER_DATA`.

## Public API

- `start_embedded`, `EmbeddedServer`, `DEFAULT_WORLD_SEED`, `default_data_folder`: used by the native client's `connection` module.
- `ServerPlugin`, `NetworkPlugin`, `headless_app`, `ServerWorld`, `Connections` (`add(link, Option<name>)` for a new client: `None` for a guest named by its `Hello`), `CharacterName`, `DATA_FOLDER_VARIABLE`, `TICKS_PER_SECOND`.

## Depends on

- `shared` (`world`, `poi`, `movement`, `protocol`, `site`, `dungeon`, `surface`), `serde`, `ron` (save files; MIT/Apache-2.0, already used by Bevy), `dirs` (the user's data folder; MIT/Apache-2.0), `axum` + `tower-http` + `tokio` (WebSockets and files on one port; MIT). Bevy with default features off plus `std`, `bevy_log`, `multi_threaded`: no rendering, windowing, audio or input, so the Docker build stays small and needs no Linux desktop libraries.

## Used by

- Native `client` (`connection`: the embedded single-player server). The web client never depends on it (target-specific dependency in `crates/client/Cargo.toml`).

## Notes

- Embedded, the server runs on its own thread ("server") as its own Bevy `App`, so it shares no components or resources with the client: everything goes through the `Link`. The `App` is built on that thread (it can't move between threads). It adds no log plugin (the client's is used; only one can exist per process). When the client hangs up (on quitting) it saves and stops, and the client waits for it; if the process is killed, at most `SAVE_EVERY` of play is lost.
- For now every poi is sent to everyone (`world_map::ALL_POIS_KNOWN`, the owner's choice: a TODO until characters can learn of them). With it off, pois are hidden until known (`world_map::known_poi`): towns are seen by all, the rest only with `KnownPoi::known` or `visited`, or after `DevRevealPois` (this connection only). Nothing sets `known` yet. Entering (`enter_poi`) checks the same thing, as a client could otherwise enter one it was never told of.
- What a character knows (world map chunks seen, with or without a poi: all sent again on connecting, for the player's map; cells of each level seen) and where they are is saved; what the client has been sent is per connection. A site's generator version is fixed when it is first entered (one per site, not per level: a site's levels must agree on their stairs). `changes` are applied but nothing makes any yet; `last_visit` is recorded for resets, which come with spawns. Dev tools sites are saved too (`SiteId::Dev`).
- Tests that need saving use `TestFolder`; everything else uses `ServerWorld::new` (nothing saved). Runs for checking visuals should set `HALL_OF_WORLDS_SERVER_DATA` to a scratch folder, so they don't move the owner's character.
- Movement is steps only (`ClientMessage::Step`): the server never takes a position from a client. There is no speed limit yet (as many steps as arrive). On the world map, water stops steps, and the server's clock sets the tide.
- Towns: the whole level is sent on entering, marked `remembered`, after `Buildings`; nothing goes into the character's memory, and `update_sight` only sends cells that have changed since (no sight is worked out).
- A saved world at world map version 1 carries on: version 2 only turned some pois into towns.
- Levels are generated again on every visit (and the other level of each staircase, to work out its way down); cheap so far.
- Uses the filesystem (saves), one reason the web client must not contain it. Its data folder is its own, never shared with a client's (a client's data will go beside it, in `Hall of Worlds/client`).
- In Docker it is the only process: it serves the web client and the game on port 8080 (`Dockerfile`).
- Characters over the network are guests: `guest-<16 hex digits>` from the number in `Hello` (no accounts yet, so anyone with the number plays that character). When a character connects again, the older connection is refused ("playing somewhere else") and saved first, then the new one loads it: `handle_messages` welcomes a client only after its `Hello` (`join`), stopping its messages there for that tick. The embedded server's one client is `player`, whatever its `Hello` says.
- When embedded in the client, the client's full Bevy features are active too (Cargo unifies features); that's fine.
